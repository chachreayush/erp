Multi-Tenant Architecture (AM / CM Model)

1.1 Account Master (AM) — Main Company

  • The primary login and top-level entity in the system.
  • AM has its own independent ERP ecosystem with full functionality.
  • AM has unrestricted access to view and manage any Client Module (CM) company and its data.
  • AM defines the master set of ERP functionalities that are available to all CMs.
  • AM grants, restricts, or revokes access to basic and special modules for each CM.
  • AM can modify CM permissions at any time after initial creation.

1.2 Client Module (CM) — Client Companies

  • Created by the AM.
  • Each CM receives access to modules as permitted by AM at the time of creation.
  • Each CM has its own CM Admin who can independently manage:
    • Roles
    • Rules
    • Restrictions
    • Access controls
  • Isolation Principle: Any roles, rules, restrictions, or access changes made by a CM affect only that CM. They have no impact on the AM or any other CM.

Data Architecture & Storage Strategy

3.1 Offline-First / Local-First

  • All data is stored locally first on the user's machine/server.
  • A local relational data engine handles all core transactions to ensure zero lag, especially during peak billing hours.
  • Micro-second lags during peak hours are unacceptable.

3.2 Cloud Sync — Isolated Per Company

  • Data syncs to the cloud in the background when internet access is available.
  • Each company's shared data is stored on a separate cloud account:
    • AM shared data → AM's cloud account
    • CM1 shared data → CM1's cloud account
    • CM2 shared data → CM2's cloud account
    • ...and so on.

3.3 Cloud-to-Local Data Protection

  • Changes made to the shared cloud database cannot directly alter the main data stored on the local system.
  • When cloud data changes (e.g., a remote user updates a record), the system sends a push notification to the local system.
  • The local admin/operator reviews and decides whether to accept those changes into the local master data.
  • This ensures the local database remains the authoritative source of truth and is protected from unintended remote modifications.

3.4 Multi-User Architecture

  • There is a main server and other users connect as clients.
  • Remote access is available via Windows, Android, and iOS applications.
  • Remote users sync to their respective company's shared database.
  • Read, write, and delete permissions for remote users are controlled by the CM Admin, which in turn is governed by the AM.

Remote Order Placement & Approval Workflow

4.1 Remote Order Placement

  • Orders can be placed from remote applications (Android, iOS, Windows client).
  • Remote orders are not final — they enter an approval queue.

4.2 Company-Specific Approval Rules

  • Each company (CM) can individually configure its own approval workflow:
    • Number of approval stages.
    • Which roles can approve at each stage.
    • Auto-approval thresholds (e.g., orders below a certain value).
  • Approval rules are managed by the CM Admin and do not affect other CMs.

4.3 Final Approval & Billing on Windows Desktop

  • The final check, approval, and billing for all orders is done exclusively on the Windows desktop application.
  • The Windows app serves as the primary billing station — no billing is finalized on mobile apps.
  • Approved orders flow into the billing/invoicing module for completion.

4.4 Approval Hierarchy Example

Field Staff (Mobile) → Places Order
       ↓
Sales Area Manager → Approves / Rejects
       ↓
Manager → Approves / Rejects
       ↓
Admin (Windows Desktop) → Final Approval + Billing

Security & Authentication

  • Two-factor authentication (2FA) for AM and CM Admin logins.
  • Encrypted data storage (at rest and in transit).

Smart Session Management

  • Persistent trusted devices — once a device is verified, it stays logged in without repeated authentication.
  • Background token refresh — sessions renew silently in the background so users are never interrupted.
  • Sensitive action re-verification — only prompt for password/PIN when performing high-risk actions (e.g., deleting records, changing permissions, financial approvals), not for routine use.
  • Role-based session rules — AM Admin can configure session policies per role (e.g., field staff sessions last longer, admin sessions require periodic re-verification).

Proposed Unified Architecture & Connectivity Model

20.1 Unified Single Application (The "One-Exe" Model)

The ERP will be distributed as a single executable file (ERP.exe) that dynamically adapts its behavior based on how and where it is launched. This eliminates the need for separate server, client, and remote applications.

  • Server Mode (Main Office PC): When run for the first time via the full setup installer, the application initializes the main local database, the backend services, and the administrative ERP interface.
  • LAN Client Mode (Local Network): Designed to match the simplicity of Marg ERP. An administrator can simply copy the ERP.exe file and paste it onto any other computer on the same local network. No installation or configuration is required. When double-clicked, the application uses UDP broadcast to automatically discover the main server on the network within 1-2 seconds and connects instantly. Users never need to manually enter IP addresses or server paths.
  • Remote Client Mode (Internet): If a user takes the exact same ERP.exe outside the office (or if the application fails to find a local server), it automatically switches to remote mode. It connects securely via the cloud bridge (using a shared cloud database) while maintaining a local offline cache so the user can continue working even if their internet connection drops.

20.2 Secure Remote Login & Credential Management

Remote access is highly secure and strictly compartmentalized to ensure data isolation between the Account Master (AM) and Client Modules (CMs).

  • Three-Field Authentication: Remote users must authenticate using three specific pieces of information: a Company ID, a Username, and a Password.
  • Auto-Generated, Permanent Company IDs: The server automatically generates a unique Company ID for the AM and every CM created. These IDs are permanent and never regenerate. This ensures that legitimate remote users are never disrupted or unexpectedly disconnected by administrative changes to the company ID.
  • Smart Credential Caching: After the first successful login, the application securely remembers the Company ID and Username. For subsequent logins, the remote user only needs to enter their password.
  • Seamless Company Routing: Because the Company ID is provided at login, the system automatically routes the user to the correct isolated database (AM or the specific CM) and applies their specific roles and permissions instantly.

20.3 Advanced Access Control & User Blocking

Administrative control over user access is granular, ensuring maximum security without collateral disruption.

  • Individual User-Level Control: If a remote user's access needs to be revoked, the AM Admin or CM Admin can block or disable that individual user's account.
  • Zero Disruption to Others: Because access is controlled at the individual user level (rather than by changing shared company credentials or regenerating the Company ID), blocking one employee will have absolutely zero impact on other remote users working within the same company.
  • Hierarchical Authority: The AM Admin retains overarching authority and can instantly block, unblock, or modify permissions for any user across the entire ecosystem, including users belonging to any CM.
