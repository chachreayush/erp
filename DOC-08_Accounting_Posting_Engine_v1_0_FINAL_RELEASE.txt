1. Purpose & Scope
The Posting Engine converts approved business events into balanced accounting entries and related financial sub-ledger records. It must be the only normal path by which application modules create official accounting effects.
BUSINESS DOCUMENT
   ↓
VALIDATE
   ↓
CALCULATE
   ↓
DETERMINE ACCOUNTS + TAX + DIMENSIONS
   ↓
BUILD POSTING PACKAGE
   ↓
ATOMIC POST
   ├── Journal Entry / GL
   ├── Party Open Item
   ├── Tax Record
   ├── Settlement Eligibility
   └── Source Link / Audit
   ↓
POSTED

2. Accounting Posting Philosophy
Post the economic event once; derive all accounting views from that posting.
Never let each module invent its own debit/credit logic.
Every posted journal must balance within the required accounting dimensions and currencies.
Every financial posting must reference its source document and company context.
Every posted document must be reproducible from stored rules and master data snapshots.
Settlement/clearing links must not duplicate the original monetary posting.
Corrections happen through controlled reversal/adjustment, not silent mutation.
Posting must be atomic, idempotent and auditable.
Company boundaries are mandatory: a posting cannot cross a client-company boundary unless a future explicit inter-company rule authorizes it.

7. Account Determination
The engine should not hard-code account numbers into screens. Account determination should resolve accounts through configurable posting rules and mappings.
TRANSACTION CONTEXT
(Customer / Supplier / Product / Principal / Warehouse / Tax / Expense Type / Transaction Type)
        ↓
POSTING RULE RESOLUTION
        ↓
MAIN ACCOUNT + PARTY RECONCILIATION ACCOUNT + TAX ACCOUNT + COST/DIMENSIONS

8. Posting Rules & Definitions
The ERP should maintain versioned posting definitions. Each definition tells the engine which conditions apply and which accounting entries result. This mirrors established ERP approaches such as Dynamics 365 posting definitions and SAP posting/clearing concepts.

9. Tax Determination
Tax calculation should occur before posting and return a structured result. The posting engine consumes that result; it should not duplicate tax formulas independently in multiple modules.
TRANSACTION → TAX ENGINE → TAX RESULT
                           ├── Tax base
                           ├── Rate/category
                           ├── Tax components
                           ├── Place of supply
                           ├── RCM/other flags
                           └── Tax account mapping
                                      ↓
                              POSTING PACKAGE
Store tax result snapshot with the posted document
Use effective-dated tax configuration
Keep statutory integration adapters separate
Validate tax totals before commit
10. Financial Dimensions & Cost Centres
The engine should support financial dimensions so the same ledger account can be analyzed by branch, principal, department, warehouse, project or other configured dimensions. Established ERP systems use account structures and default/fixed financial dimensions to control valid combinations during posting.

11. Customer / Supplier Open Items
Party invoices, credit/debit notes, advances and eligible financial documents should create open-item records. Outstanding is a view of open items and their settlement state, not a manually maintained balance.
INVOICE → OPEN ITEM
PAYMENT → PAYMENT OPEN ITEM / SETTLEMENT SOURCE
CREDIT NOTE → CREDIT OPEN ITEM
DEBIT NOTE → DEBIT OPEN ITEM
           ↓
     SETTLEMENT / CLEARING
           ↓
      OPEN AMOUNT CHANGES

12. DOC-07 Bill-by-Bill Settlement Integration
DOC-07 is mandatory for the posting engine. The engine must create settlement-eligible open items and consume explicit allocation instructions without duplicating financial effects.

13.1 Direction rules
A customer payment normally reduces a customer debit/open receivable item.
A customer credit note normally reduces receivable exposure and can be allocated to eligible invoices.
A customer debit note normally increases receivable exposure and cannot be treated as a payment merely to make an invoice disappear.
Supplier-side documents use the mirrored payable logic.
Cross-party netting is disabled by default and requires explicit policy/relationship authorization.

19. Atomicity, Idempotency & Duplicate Protection
19.1 Atomicity
POSTING TRANSACTION
├── Journal Header
├── Journal Lines
├── Open Items
├── Settlement instructions
├── Tax records
├── Stock accounting link
└── Audit event
       ↓
ALL COMMIT or ALL ROLLBACK
19.2 Idempotency
Every posting request carries a unique idempotency key derived from source document + posting attempt/version.
Retrying the same request returns the original posting result instead of creating duplicate entries.
Sync retries cannot create duplicate journals.
Settlement retries cannot create duplicate allocation rows.
19.3 Duplicate guards
UNIQUE(source_company, source_document_id, posting_version, posting_action)
UNIQUE(settlement_source_id, allocation_idempotency_key)

22. Multi-Company / Platform Security
PLATFORM → COMPANY → BRANCH → WAREHOUSE / DIMENSION → USER / ROLE → POSTING
Posting must execute inside a company context.
Client company cannot post into the Platform Admin company.
Platform Admin access is separately attributed and audited.
Cross-company posting requires explicit future intercompany capability.
Every query and posting service validates tenant/company authorization server-side.
23. Local-First & Live Cloud Posting
Posting must work within the local-first architecture defined in DOC-04. Remote users interact with the live cloud transactional state; local and cloud posting paths must use the same business rules and posting package model.
LOCAL USER → LOCAL POSTING ENGINE → LOCAL DB → LIVE CLOUD SYNC
REMOTE USER → CLOUD TRANSACTION LAYER → SAME POSTING RULES → CLOUD STATE → LIVE SYNC TO LOCAL
Same source IDs and posting rules
Idempotent sync
Version/sequence validation
No duplicate financial effect
Clear last-synced/posted state
Conflict routed to controlled resolution

28. Error Handling & Recovery

Appendix C. Non-Negotiable Invariants
1. Every posted journal balances.
2. Every journal has a company context.
3. Every posting has a source document and idempotency key.
4. Posted history is not silently rewritten.
5. Settlement does not duplicate monetary posting.
6. Outstanding is derived from open items and settlement state.
7. Payment, credit note and debit note retain their own document identity even when settled together.
8. Client companies cannot post into Platform Admin accounting.
9. Rules are versioned and explainable.
10. Local and remote posting paths use equivalent business rules.
11. Failed/partial posting is rolled back atomically.
12. All sensitive overrides are permission and audit controlled.

Final Specification Statement
DOC-08 establishes the Accounting Posting Engine as the single controlled financial execution layer of the ERP. DOC-07 defines what may be settled against what; DOC-08 ensures those settlement instructions interact with correctly posted invoices, payments, credit notes, debit notes, advances, expenses, freight, inventory and tax without duplicate or missing accounting effects.
