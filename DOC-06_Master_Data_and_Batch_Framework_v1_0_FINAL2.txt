1. Purpose & Scope
This document defines the common master-data framework that every future ERP module must use. It does not replace the detailed module implementation documents for Billing, Accounting, Inventory, Purchase, CRM, Principal Management or GST; instead, it defines the trusted records those modules consume.
MASTER → VALIDATION → TRANSACTION → LEDGER / MOVEMENT → REPORT

2. Master Data Philosophy
One master record = one controlled business identity within its company scope.
Masters have stable internal IDs; display codes/names can be changed under controlled rules.
Referenced masters are normally deactivated, not deleted.
Every master has company scope unless explicitly declared platform/system scope.
Effective dates are used for rules that change over time, such as prices, taxes and schemes.
Operational transactions should not overwrite master history silently.
Batch identity belongs to inventory traceability and must be linked to stock movements.
Product and batch are separate entities: product describes what the item is; batch describes a specific identifiable quantity/group.
Company ownership, warehouse location and batch are separate dimensions.
All masters must work with keyboard-first search and quick creation.

COMPANY USERS
    ↓ use masters according to role/scope

6. Master Lifecycle
DRAFT / SETUP → ACTIVE → BLOCKED / INACTIVE → ARCHIVED
New masters can begin as Draft when they require review or mandatory setup.
Active masters can be used in transactions.
Blocked masters remain searchable for history but are prevented from new transactions according to the rule.
Archived masters remain for historical reporting and audit but are not selectable for new activity.
Deletion is allowed only for unreferenced draft/setup records under controlled permission.

11. Batch / Lot Management — Core Architecture
Batch/lot management is a first-class feature of this ERP. It is especially important where products are perishable, regulated, recall-sensitive or commercially differentiated by manufacturing batch. Established ERP systems use lots/batches for traceability, expiration and lifecycle tracking; this document takes those patterns as design references while keeping the C&F ERP configurable and company-specific.
PRODUCT
   ↓
BATCH / LOT
   ├─ Batch number
   ├─ Manufacturing date
   ├─ Expiry date
   ├─ Best-before / removal / alert dates
   ├─ Supplier / source
   ├─ Principal / owner
   ├─ Quality / status
   └─ Additional characteristics
   ↓
STOCK POSITIONS
   ↓
RECEIPT → TRANSFER → SALE → RETURN → ADJUSTMENT
   ↓
TRACEABILITY REPORT
11.1 Batch identity rules
Batch number is unique within the defined identity scope; the scope should be configurable (for example company + product, or company + principal + product where needed).
A batch must always be linked to a product.
A batch cannot be reassigned to a different product after it has been used in stock movements.
Batch quantity is derived from stock movements; it is not an independently editable balance.
Batch-specific attributes must remain available for historical reporting.
If the same physical batch is received into multiple warehouses, the ERP should keep one batch identity with multiple stock positions rather than create unrelated batch identities.

15. Batch Traceability & Recall
A user should be able to start from either a batch or a transaction and navigate the full chain of custody.
BATCH → RECEIPT → SUPPLIER / PRINCIPAL → WAREHOUSE → TRANSFERS → DISPATCH → INVOICES → CUSTOMERS → RETURNS
15.1 Traceability questions the ERP must answer
Where is this batch now?
How much remains?
Where did it come from?
Which supplier/principal supplied it?
Which invoices used it?
Which customers received it?
How much was returned?
Was any quantity damaged/expired?
Which warehouses hold it?
Which transactions changed it?

16. Batch Allocation & FEFO/FIFO Rules
The system should support configurable allocation rules instead of assuming one method for every business.

16.1 Recommended default for expiry-controlled products
AVAILABLE BATCHES → REMOVE EXPIRED/BLOCKED → SORT BY EXPIRY → SUGGEST EARLIEST VALID BATCH → USER CONFIRMS → RESERVE/ISSUE
The user must be able to override an automated suggestion only when the business rules permit it. An override should record the reason when configured.

18. Batch Controls in Sales & Billing
INVOICE LINE → PRODUCT → SHOW AVAILABLE BATCHES → EXPIRY / QTY → FEFO SUGGESTION → SELECT/CONFIRM → RESERVE → POST STOCK OUT
Show available qty per batch
Show expiry prominently
Warn/block expired batch
Show blocked/quarantine batches but prevent use
Allow multiple batches against one invoice line where needed
Print batch/expiry on documents where configured
Preserve exact batch allocation in accounting/stock source records

19. Batch Controls in Returns & Adjustments
Returns must identify the batch when the original sale was batch-tracked
Returned stock should initially enter the appropriate return/quarantine state according to configured rules
Do not automatically make returned goods available for sale if quality inspection is required
Batch quantity changes only through controlled stock movements
Adjustments require reason and appropriate permission

41. Acceptance Criteria
1. Every company has isolated masters unless an explicit platform/shared rule exists.
2. Product tracking mode determines whether batch entry is mandatory.
3. Batch records are separate from Product records.
4. Batch quantities come from stock movements rather than manual balance edits.
5. Expiry-controlled batches cannot be sold when expired unless a controlled exception is explicitly configured.
6. Traceability can move from batch to source receipt and downstream transactions.
7. Batch selection is available in keyboard-first billing without unnecessary navigation.
8. Small businesses can operate with minimal master complexity.
9. Large businesses can activate advanced batch, principal, warehouse and permission functionality.
10. Master updates synchronize according to the live cloud architecture.
11. All sensitive changes and overrides are auditable.
42. Non-Negotiable Rules
1. Product and Batch are separate concepts.
2. A Batch must belong to exactly one Product within its company scope.
3. Batch stock is derived from movement history.
4. Expired/blocked/quarantined batches cannot silently become sellable.
5. Batch identity cannot be changed after posted stock usage.
6. Customer, supplier, principal and product masters are company-isolated by default.
7. Master lifecycle must protect historical reporting.
8. Effective dates must be used for rules that change over time.
9. Batch allocation must be auditable.
10. Keyboard-first search and selection applies to all high-volume masters.
11. No module should create duplicate master logic outside the common master framework.
12. All master changes must respect Platform Admin permission ceilings and company permissions.

Appendix D. Future Detailed Documents

Final Design Position
The Master Data Framework should make the ERP feel simple to the operator while preserving the data structure needed for serious accounting, distribution and C&F operations. The most important decision in this document is to treat Batch/Lot as a first-class inventory identity: Product defines the commercial item, Batch defines the traceable group, Stock Position defines where and how much exists, and Stock Movement defines how the quantity changed.
