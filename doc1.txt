2. Executive Summary
The ERP is designed as a highly scalable, multi-tenant C&F platform that prioritizes data sovereignty, operational speed, financial integrity and usability. The intended product combines a central Platform Administration layer with independently operated client companies. Each client company owns its own users, permissions, masters, inventory, billing, accounting, reports, settings and data.
The system is local-first for heavy transaction operations. A client company can operate a primary local server, while multiple LAN users connect to that primary node for high-volume billing, inventory, accounting and operational work. Remote users access an appropriate remote state through a synchronization architecture. Synchronization must be designed as a transactional system, not as an unsafe file-copy mechanism.

3. MASTER PRODUCT PHILOSOPHY
The product philosophy describes the beliefs that should guide every design decision. When a future feature request is ambiguous, the product philosophy is the first lens used to decide how the system should behave.
3.1 Principle: Business-first, technology-supported
Technology should serve the real C&F workflow. The user should describe the business event once; the system should perform the repetitive calculation, posting, cross-module updates and reporting automatically.
3.2 Principle: Simple on screen, rigorous underneath
The interface should remain understandable to an operator while the backend maintains strong rules, audit trails, calculations and transactional integrity.
3.3 Principle: One business event, many automatic consequences
ONE POSTED INVOICE
   ├── Stock movement
   ├── Customer receivable
   ├── Revenue
   ├── Tax records
   ├── Cargo / freight
   ├── Logistics cost
   └── Reporting / MIS
3.4 Principle: No duplicate entry when the system already knows
Customer GST details should come from the customer master.
Product tax/HSN/UOM data should come from product configuration.
Payment terms should calculate due dates.
Freight should be calculated from cargo/rate rules where configured.
Accounting entries should come from posting rules.
Outstanding balances should come from financial transactions and allocations.
3.5 Principle: Fast for high-volume users
Billing and warehouse operations must optimize for keyboard use, search, predictable navigation and minimal mouse movement.
3.6 Principle: Powerful without becoming confusing
Advanced facilities should be available through progressive disclosure, collapsible sections, role-based visibility and contextual actions instead of putting every field on one screen.
3.7 Principle: Financial truth is immutable
Posted accounting effects should not be silently rewritten. Corrections use controlled workflows such as reversal, return, credit note, debit note or adjustment.
3.8 Principle: C&F is the core domain, not an add-on
Cargo, principal, stock ownership, transporter, freight, loading, unloading, recovery and logistics profitability must be native concepts.

6. Local-First Execution & Live Synchronization Philosophy
6.1 Primary local node
The local primary server is the authoritative transaction processor for a client office when local-first mode is enabled. LAN clients connect to it for high-volume operations.
LOCAL PRIMARY SERVER
 ├── Local transactional database
 ├── Posting engine
 ├── Inventory engine
 ├── Accounting engine
 ├── Billing engine
 ├── Sync engine
 └── Local audit log
        ↑  ↑  ↑
      LAN CLIENTS
6.2 Remote/light access
Remote users can perform permitted lighter tasks against the synchronized remote state. The remote architecture must not assume that cloud object storage itself is the transactional database.
6.3 Synchronization principles
Each change receives a unique event/change ID.
Every sync operation is idempotent.
Ordering is tracked for dependent changes.
The source of authority for each object/state is explicit.
Acknowledgements prove receipt/application.
Retries must not duplicate transactions.
Conflicts are detected and resolved by policy, not silently overwritten.
Critical financial posting should not be duplicated by replay.
Offline work, if supported, uses a durable local queue.

7. Keyboard-First ERP Philosophy
Keyboard operation is not a cosmetic shortcut feature. It is a product principle. The ERP should be engineered so high-volume users can work quickly without repeatedly moving between keyboard and mouse.
7.1 Global keyboard system

Actual key choices should be finalized in the keyboard-standard document and must avoid collisions with browser/OS shortcuts where possible.
7.2 Keyboard principles
Every primary action has a visible shortcut.
Focus order is predictable.
Dropdowns are searchable by typing.
Tables support row navigation without mouse dependency.
Barcode/product entry supports immediate keyboard flow.
The system never traps focus unexpectedly.
Modal dialogs have clear Esc/Enter behavior.
Destructive actions require confirmation and should not be a single accidental key press.

8. Crash Recovery & Continuity Philosophy
The ERP should assume that terminals can crash, networks can drop and users can close windows accidentally. In-progress work must therefore be recoverable without corrupting posted accounting.
USER ENTERS DATA
   ↓
LOCAL DRAFT AUTOSAVE
   ↓
CRASH / POWER FAILURE
   ↓
REOPEN MODULE
   ↓
RECOVER DRAFT
   ↓
USER REVIEWS
   ↓
POST ONLY AFTER VALIDATION
Drafts must never be treated as posted accounting.
Autosave frequency should be configurable within sensible limits.
Recovered drafts should show last-saved time and source terminal/user.
Duplicate posting protection must use idempotent transaction keys.
9. Financial & Accounting Integrity Principles
9.1 Three-level accounting hierarchy
LEVEL 1 — ACCOUNT CLASS
Assets / Liabilities / Income / Expenses
      ↓
LEVEL 2 — GROUP / SUB-GROUP
Current Assets / Current Liabilities / Warehouse Expenses...
      ↓
LEVEL 3 — POSTING LEDGER
Customer / Bank / Sales / Expense / Tax ledger
9.2 Protected ledgers
Core system ledgers cannot be deleted.
Referenced ledgers cannot be deleted.
Changing names/codes must preserve internal IDs and audit history.
Posting destinations must remain valid.
9.3 Bill-by-bill allocation
Receipts should be allocatable to exact invoices, multiple invoices or on-account balances while preserving an allocation history.
RECEIPT ₹100,000
   ├── Invoice A ₹40,000 → Allocated
   ├── Invoice B ₹35,000 → Allocated
   └── On-account ₹25,000 → Unallocated
9.4 Financial non-negotiables
Balanced journal entries
Controlled posting periods
No hidden ledger edits
Source document links
Reversal/adjustment workflow
Audit trail
Report drill-down

The conversion must reuse authoritative challan information rather than force the operator to re-enter every item.
10.2 Smart MRP / pricing
The pricing engine may suggest a selling price based on the active price list, product/customer/principal rules, configured commercial schemes and effective dates. User overrides should require appropriate permission/reason where policy requires.
10.3 C&F cargo-native workflow
ORDER / REQUEST → DISPATCH → CONSIGNMENT → FREIGHT → EXPENSES → RECOVERY → BILLING → ACCOUNTING → PROFITABILITY
11. Security, Identity & Data Governance Principles
Identity is global only where necessary; business data is company-scoped.
Every API request establishes a trusted company context.
Server-side authorization is mandatory; UI hiding is not security.
Exports and bulk operations are permission-controlled.
Sensitive cost/margin information has separate permissions.
Administrative cross-company access is auditable.
Backups preserve company isolation.
Attachments inherit access control from the source document.

15. Anti-Patterns — What This ERP Must Not Become
A collection of disconnected screens.
A system where accounting balances are manually edited.
A system where each report calculates its own version of the truth.
A system where company A can accidentally query company B.
A system requiring constant mouse use for billing.
A system that copies files to cloud and calls that live synchronization.
A system where posted invoices can be silently overwritten.
A system where every setting is hard-coded.
A system with unlimited admin powers and no audit trail.
A system where AI-generated code is deployed without tests.

20. Final “North Star” for the ERP
When deciding whether a feature belongs in the product, the following questions should be asked:
Does this make the real C&F business process faster or safer?
Does it preserve company data separation?
Can the user perform it efficiently with the keyboard?
Does it create a single authoritative source of truth?
Does it preserve accounting/stock/tax integrity?
Does it remain auditable?
Can it recover safely from failures?
Can the feature be understood and maintained by future developers?
Does it fit the document/module boundaries defined in this master plan?
