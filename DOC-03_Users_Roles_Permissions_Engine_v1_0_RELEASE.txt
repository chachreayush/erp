1. Purpose and Scope
DOC-03 defines how identity, roles, permissions and administrative scope work throughout the ERP. It converts the platform hierarchy defined in DOC-01 and the authentication/session behavior defined in DOC-02 into an enforceable authorization system.
PLATFORM / MASTER ADMIN
        │
        ├── defines permission ceiling
        ├── creates client company
        ├── provisions initial roles
        └── can administer platform scope
                ↓
        CLIENT COMPANY
                │
        COMPANY ADMIN
                │
        ├── users
        ├── roles
        ├── company permissions
        └── operational scope
                ↓
       COMPANY USERS
This document does not define every module-specific permission. Instead, it defines the engine that later documents will use. Each future module must publish its permission catalog and its default role mapping within this framework.
2. Permission Philosophy
Permissions are a security boundary, not a UI convenience.
Never depend on hiding a menu item as the only protection; authorization must be enforced server-side and at the data/service layer.
The client company is autonomous for its own administration but subordinate to the platform boundary.
Client admins may delegate downward, never upward.
Platform Admin permissions must never be assignable by client users.
Permission scope should be as narrow as practical: company, branch, warehouse, module, document type, action and sometimes field or record set.
Default access should be minimal; privileges are added deliberately.
Financially sensitive actions such as posting, reversal, deleting masters, changing opening balances and viewing cost/margin can require separate permission.
Permission changes must be auditable and should have effective timestamps.
Role templates should make setup fast, while custom permissions handle unusual business needs.

5. User Identity Model

5.1 One person vs one user account
The preferred design is one global identity with one or more company memberships rather than multiple unrelated login identities for the same person. The active company context is then selected at login or switched through an authorized company switcher. Where strict separation is required, a company-specific identity can still be used, but the authorization engine should treat company membership as the decisive scope.
6. Role Model
A role is a reusable bundle of permissions. A user may receive one or more roles; the effective permission set is the union of allowed permissions subject to explicit deny rules, scope limits and platform ceilings.

  ↓
PERMISSIONS
  ↓
SCOPE
  ↓
EFFECTIVE ACCESS

11. Client Company Permission Delegation
The Client Company Admin can create their own roles and assign permissions for company users, but the effective permission of any company user can never exceed the company’s platform-defined ceiling.
PLATFORM ADMIN
   ↓ establishes ceiling
COMPANY ADMIN
   ↓ creates role
ROLE
   ↓ assigns permitted permissions
USER
   ↓
EFFECTIVE PERMISSION = ROLE PERMISSIONS ∩ PLATFORM CEILING ∩ USER / SCOPE LIMITS

16. Role Lifecycle
SYSTEM TEMPLATE → CLONED → CUSTOMIZED → ACTIVE → DEPRECATED → ARCHIVED
Do not silently change an active role in a way that surprises existing users. Major changes should be versioned or audited.
When a role is retired, users should be reassigned or moved to a replacement role.
A deleted role should normally be soft-deleted/archived if it has historical assignments.

24. Permission Evaluation Engine
Every protected request should resolve authorization through one consistent policy engine rather than scattered if/else logic in individual screens.
REQUEST
 ↓
IDENTITY
 ↓
ACTIVE SESSION
 ↓
ACTIVE COMPANY CONTEXT
 ↓
USER MEMBERSHIP
 ↓
ROLE(S)
 ↓
PERMISSIONS
 ↓
PLATFORM CEILING
 ↓
SCOPE FILTERS
 ↓
CONDITIONS / FIELD RULES
 ↓
ALLOW / DENY + AUDIT EVENT
24.1 Pseudocode concept
authorize(user, company, resource, action, context):
  assert authenticated
  assert active company == requested company
  assert user has membership in company
  ceiling = platform_ceiling(company, resource, action)
  if ceiling == DENY: return DENY
  roles = active_roles(user, company)
  grant = union(role permissions)
  scope = effective_scope(user, roles, company)
  if not grant.includes(resource, action): return DENY
  if not scope.allows(context): return DENY
  if condition_fails(context): return DENY
  return ALLOW
25. Caching & Performance
Cache role/permission definitions safely with version numbers.
Invalidate permission cache immediately after a permission change where possible.
Never cache authorization decisions longer than policy permits.
Use server-side policy evaluation for sensitive operations.
For LAN/offline use, maintain a signed/validated authorization snapshot that can support local operation according to security policy.
Permission changes must propagate through sync and should include a version or epoch number so stale permission sets can be detected.

28. Local/LAN + Sync Considerations
Because this ERP is local-first, authorization must work locally while still converging correctly with the platform/cloud state.
PLATFORM PERMISSION CHANGE
        ↓
AUTHORITY VERSION ++
        ↓
CLOUD / SYNC EVENT
        ↓
LOCAL PRIMARY SERVER
        ↓
LAN CLIENTS RECEIVE UPDATED POLICY

A permission change should have a monotonic version/epoch.
Critical revocations should be designed to propagate as a priority event.
A disconnected client should not be allowed to invent a permission the local server did not authorize.
Sensitive platform policy changes should be rejected offline if current authority cannot be verified, according to the security policy.
Permission sync must be idempotent and auditable.

32. Small-Business vs Large-Business Modes
The same permission engine should support both. Complexity should be progressive rather than architectural duplication.


33. Acceptance Criteria
A newly created client company receives only the permissions defined by the Platform Admin ceiling.
Company Admin can create a custom role using allowed permissions.
Company Admin cannot create or assign a Platform Admin role.
Company Admin cannot access another client company unless explicitly given separate membership by Platform Admin.
Client users cannot access Platform Admin screens or APIs.
Permission checks occur server-side.
User permissions can be limited by branch and warehouse.
High-risk permissions can be separated from general module access.
Permission changes are audited.
Permission changes propagate through local/cloud sync with versioning.
Permission revocation takes effect within the defined security SLA.
Effective access can be inspected for any user.
Role changes do not silently overwrite another administrator’s concurrent edits.
All sensitive admin actions leave an audit trail.
34. Non-Negotiable Rules
1. Platform Admin controls the permission ceiling; Client Admin controls only what exists below that ceiling.
2. Client Company permissions never grant access to the Platform Admin / Master Company layer.
3. A company admin may not elevate themselves above the ceiling.
4. Every role assignment is scoped to an explicit company membership.
5. No browser-provided company/role/permission identifier is trusted without server authorization.
6. Posted financial permissions remain subject to Accounting module rules and segregation-of-duties controls.
7. Permission changes are auditable and versioned.
8. Permission denial is the default when policy cannot be resolved safely for sensitive actions.
9. Local-first operation never becomes a backdoor around platform authorization.
10. Future modules must publish their permission catalog using this engine rather than inventing their own authorization system.

Implementation Conclusion
DOC-03 establishes a hierarchical authorization model that preserves the separation defined in DOC-01 while allowing each client company to manage its own workforce. The key idea is not “one global permission list”; it is a layered policy: platform ceiling → company role → user membership → operational scope → action/condition → audit.
This makes the same ERP suitable for a small business that needs a handful of simple roles and a large organization that needs delegated administrators, branch/warehouse scope, approval chains and sensitive-data controls—without creating different products or security models.
