DOC-04
LOCAL-FIRST, LAN & CLOUD LIVE TRANSACTIONAL ARCHITECTURE
Local installation • LAN high-volume operations • compact live cloud transaction tier • remote users • continuous synchronization • automatic backup

Architectural requirement captured in this version
The ERP is installed on the client’s local computer/local server for primary business operations. Remote users must access a compact, live cloud version of the company’s transactional ERP data. The cloud tier is not merely a backup: it is a live transactional data tier for remote users and is automatically synchronized with the local primary environment. The same cloud storage architecture also provides backup capability.
Important implementation boundary
Google Drive, OneDrive/SharePoint, or another supported low-cost provider may be used as the cloud persistence provider. The ERP must not open one SQLite/database file directly from a shared drive. Instead, the ERP must store transaction records/events as application-controlled objects and enforce transaction ordering, version checks, idempotency, commits, retries and reconciliation in its own application layer.

1. Purpose and Scope
This document defines the architecture for the ERP deployment model in which the software runs primarily on local hardware, LAN users perform high-volume transactions locally, and remote users access a compact live cloud transactional data tier. It also defines how the same cloud storage layer supports automatic backup.
The purpose is to make the ERP inexpensive to operate for small businesses while remaining capable of serving large businesses with more users, branches, warehouses and transaction volume. The architecture should scale by increasing processing/storage capacity and synchronization capacity rather than changing the fundamental product model.
2. Architecture Decision Summary

3. Product Philosophy for Local-First ERP
HIGH-VOLUME / HEAVY WORK → LOCAL SERVER → FAST COMMIT
LIGHT / REMOTE WORK → LIVE CLOUD TIER → AUTOMATIC SYNC → LOCAL PRIMARY
                         ↓
                    BACKUP / RECOVERY
Local-first does not mean remote users see stale data by design; the cloud tier is intentionally live and is updated continuously when connectivity exists.
Cloud storage is not treated as a shared executable database file. The ERP owns transaction semantics.
Remote data is deliberately compact. The system should synchronize what remote roles actually need, not the entire local working set by default.
Every accepted transaction receives a stable identity so the same transaction cannot be created twice during retries.
The user should see the state of a transaction: pending sync, synced, conflict, rejected, or failed—not an unexplained disappearance.
Live data meaning
For this ERP, “live cloud database” means the cloud transactional tier is automatically updated as transactions occur and is continuously available to authorized remote users. It does not mean that a cloud file provider offers the same transactional semantics as a traditional relational database. The ERP application layer must provide those semantics.

9. Cloud Transactional Data Tier
The cloud tier is a live transactional representation of the company’s remote-accessible ERP state. It is intentionally compact and designed around provider APIs instead of allowing arbitrary concurrent file editing.
9.1 What lives in the cloud tier
Company identity and status needed for remote login
Remote-visible masters
Remote-visible current balances/summary data
Remote-visible transactions
Pending remote transaction events
Indexes/manifests
Version and revision metadata
Audit/sync metadata
Documents or references as configured
Encrypted backup packages
9.2 What does not have to live remotely
Large local caches
Unneeded historical detail
High-volume intermediate working data
Temporary barcode/scanner files
Internal server diagnostics not needed remotely
9.3 Live data requirement
LOCAL COMMIT → CLOUD UPDATE → REMOTE USERS SEE UPDATED STATE
REMOTE COMMIT → CLOUD UPDATE → LOCAL SERVER APPLIES → OTHER USERS SEE UPDATED STATE
Live synchronization target
The product should continuously attempt synchronization and should expose the current sync age/status. “Live” should be implemented as automatic change propagation as soon as the network and provider are available; the UI must not pretend a transaction is synchronized while it is still queued.

12.1 Source-of-truth rule
For a heavy local transaction, the local primary is the first authoritative processor. For a remote light transaction, the cloud transaction tier can accept the request first, but the final application to the full local operational database must be acknowledged. Both paths carry the same immutable transaction identity.

15. Remote Write Transactions
Remote users should not be limited to read-only access. The architecture supports controlled remote writes for tasks that the company enables, while protecting heavy, high-risk operations behind local processing or approval when necessary.

Safety principle
Remote access should expand business mobility without bypassing the local accounting/inventory controls. High-risk transactions can be accepted as “requests” in the cloud and become posted only after local validation/approval.
16. Consistency, Concurrency & Conflict Control
16.1 Consistency model
The ERP should aim for strong consistency within a single transaction and controlled near-real-time convergence between local and cloud projections. The system should never silently produce two final versions of the same financial transaction.
16.2 Concurrency

18. Provider Abstraction
The ERP should not be permanently hard-coded to Google Drive or OneDrive. Build a storage-provider adapter interface so a company can use a supported provider without rewriting the ERP.

Provider neutrality
Google Drive documents change logs, revisions, quotas and an application-data area; Microsoft Graph exposes delta queries and eTag-based conditional writes. These capabilities are useful building blocks, but the ERP must still own transaction ordering and business validation.

22. Recovery & Disaster Scenarios

23. Offline / Internet Failure
The local ERP must continue operating for LAN users during normal internet outages. Remote users cannot expect cloud access when their cloud provider/network is unavailable, but the ERP must make the last known cloud state visible with a clear freshness timestamp.
INTERNET DOWN
LOCAL USERS → CONTINUE
LOCAL TRANSACTIONS → OUTBOX
REMOTE USERS → LAST CLOUD STATE + STALE STATUS
INTERNET RESTORED → OUTBOX FLUSH → CLOUD CATCH-UP → REMOTE STATE CURRENT
24. Storage Quota & Provider Limits
Track storage usage per company
Track API call/error/throttle rates
Prefer compact record/event objects
Avoid rewriting huge monolithic database files
Batch compatible operations
Compress archival/backup bundles
Alert before quota exhaustion
Allow provider migration/export
Record provider health
Cost-control philosophy
The architecture is designed to minimize additional infrastructure spending, but “free” provider limits are not guaranteed permanently. The application should be able to detect a limit, operate locally, preserve pending transactions, and allow migration to another supported storage provider.

30. Audit Trail

31. Failure & Edge Cases
Remote user closes browser after submitting
Transaction remains in cloud committed state and is not lost. On next login, the system shows pending/applied/rejected status.
Network drops after cloud commit but before response
Retry uses the same transaction ID. The server returns the existing result instead of creating another record.
Two remote users update same customer
Version conflict is detected. A safe merge or explicit resolution is used; silent last-write-wins is avoided for financial fields.
Local user posts while remote changes same invoice
Posting engine locks/version-checks the invoice. One result becomes authoritative and the other receives a conflict workflow.
Provider API throttles
Queue remains durable; backoff occurs; users see a non-destructive sync warning.
Cloud object deleted accidentally
Audit/recovery process restores from known committed state; destructive provider operations are restricted where possible.

33. API / Service Responsibilities

34. Implementation Rules
1. Never share a raw database file between multiple computers over Drive/OneDrive.
2. Every transactional record must have an immutable identity.
3. Every remote write must be idempotent.
4. Every cloud transaction must carry company context.
5. Every sync operation must be retry-safe.
6. Every financial transaction must remain traceable from cloud event to local posting.
7. No sync failure may silently duplicate money, stock, customer balance or invoice values.
8. Users must see whether data is current, pending or stale.
9. Cloud storage credentials must be separated from business-user credentials.
10. Backup success must be verified, not assumed.
11. Provider-specific APIs must be isolated behind adapters.
12. Changing cloud providers must not require redesigning business modules.

Appendix D. Non-Negotiable Rules
1. The cloud tier is a live transactional component for remote users, not merely a backup folder.
2. Local primary remains the high-volume operational environment.
3. Remote users receive live updates automatically whenever connectivity/provider availability permits.
4. Remote writes can be enabled by permission and transaction type.
5. High-risk financial/stock operations can require local validation/approval before becoming finally posted.
6. No raw shared database file may be concurrently opened by multiple machines from cloud storage.
7. Provider APIs are infrastructure; ERP transaction semantics remain in ERP services.
8. Company data is isolated at every layer.
9. Every transaction is uniquely identifiable and retry-safe.
10. No hidden stale state: show freshness and sync status.
11. Automatic backup is part of the architecture, not a manual afterthought.
12. Provider failure must not destroy locally committed transactions.
